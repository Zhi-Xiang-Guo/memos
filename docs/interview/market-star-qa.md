# MemOS 社招 STAR 增补卷：3 主问、25 追问

更新：2026-09-07。与[主卷](../../面经-MemOS.md)合计 25 个主问、50 个追问、75 段完整作答。以下是基于仓库的第一人称练习稿，不是替用户认证独立掌握；“我会”表示方案，“已验证”才表示完成。题源 ID 见[市场研究](../research/market-2026-09-07/README.md)。

## 主题六：消费者故障、工具合同与业务结果

### Q23：接口用例全部通过，为什么真实 Agent 仍然用不了？

S：我把 MemOS 接入 Waku 后，原先的 live conformance 验证了六方法接口，但市场面经追问的是用户能否真正完成任务。T：我要验证从工具输入到后端状态再到用户输出的整条链，而不是只证明 Python 方法存在。A：我沿管理工具读取 ID 的路径检查，发现工具把 UUID 强转整数；同时用失败 opener 复现网络错误被翻译成空列表。随后保留真实空命中返回值，让读错误上浮为内容安全异常，并让工具原样传递后端 ID，补上先红后绿的回归。R：本轮 Waku 确定性门禁为 630 passed、73 skipped，修复了两个明确合同问题；未重新执行 live conformance，也没有证明真实任务成功率提升。部分更新与安全重试仍是下一层工作。

#### F26：失败为什么不能统一返回空列表？

S：在记忆管理工具里，空列表会被直接解释成“没有匹配事实”，这与服务器根本没有执行查询是不同状态。T：我需要让模型和用户知道当前结果是不确定，而不是给一个看似正常的否定答案。A：我让有效零结果继续返回空列表，让网络失败和 malformed response 抛出内容安全的 MemosError，再通过工具注册器检查最终文本确实是执行错误；同时压住底层异常链，避免响应内容出现在普通格式化 traceback。R：这一改变让错误可见，但不等于整个 Agent 已具备优雅降级；上游 gated retrieval 还需要明确选择中止、提示不可用或经授权的降级策略，不能偷偷换成无范围限制的存储。

#### F27：UUID 不过工具层，为什么适配器测试没有发现？

S：适配器直接调用时，fact ID 是合法 UUID，测试可以全部通过；管理工具却假设所有后端都像 SQLite 一样使用整数。T：我要检查消费者是否破坏了后端拥有的标识，而不是只在适配器里加更多转换。A：我从 search_with_ids 的返回字段追到 update/delete 的入口，写了整数、数字字符串、UUID、普通字符串四种 ID 的参数化测试，先观察强转失败或类型变化，再取消事实工具的整数强转。R：现在工具按合同原样传递 ID，由实际存储验证合法性；这说明跨语言和跨层测试要覆盖数据流，不能只验证各层单独“看起来正确”。它不是新增 ID 系统，也不改变已有 SQLite 存储主键。

#### F28：模型写入成功，但旧事实失效失败，应该怎样回答？

S：Waku update 是多个 HTTP 请求：先写新来源并等待，再失效旧版本，因此中间失败可能留下新旧并存。T：我必须避免把“不确定是否完成”显示成“没有这个事实”或直接再次新增。A：我会把操作拆为持久步骤，保存操作 ID、请求摘要和已完成阶段，先查询 authority 的源事件与版本状态，再决定续做失效还是人工确认；对陈旧 If-Match 重新读取后检查原用户意图是否仍成立，而不是覆盖其他人的更新。R：这是待实施的恢复合同，本轮没有宣称实现原子更新。现有多请求 update 仍可能部分完成，真实部署前应优先补这项，而不是靠一次检索没看到旧值就宣布全局收敛。

#### F29：超时之后重试，幂等键该由谁保存？

S：网络超时只说明客户端没拿到确定回执，服务端可能已经提交。T：我需要同一个逻辑操作在多次尝试中保持同一身份，同时不把后续新的用户修改误当重复请求。A：我的方案是调用方在首次提交前生成并持久保存 operation ID、canonical payload 摘要和目标范围；重试复用该键，同键异体必须拒绝。服务端用唯一约束处理竞态，并记录已完成阶段；遇到未知结果先查操作回执，不能每次 uuid4。R：MemOS 受理层已有幂等合同，Waku 每次外部调用仍会生成新身份，这个差距必须写进待办。不能把“服务端支持幂等”偷换成“整个 Agent 重试一定安全”。

#### F30：设置了 15 秒 socket timeout，就有 15 秒任务 SLA 吗？

S：一个任务可能包含队列、多个 HTTP 调用、重试和轮询，每次 15 秒并不会让总耗时最多 15 秒。T：我要区分连接或读超时、单次尝试预算、阶段预算与整个任务 deadline。A：我会注入单调时钟，在每次调用前计算剩余预算，用 min(单次上限,剩余预算) 约束下游，同时传递取消并限制重试次数；再以 fake clock 和故意慢的下游验证不能在 deadline 后继续发请求。R：这是 Waku 当前剩余的合同缺口，本轮只修读错误和 ID，并没有完成硬 deadline。即使调用前后检查时间，也不能声称阻塞第三方库一定可被及时打断。

#### F31：什么时候允许降级，什么时候必须停下来？

S：检索或模型服务失败时，直接退回旧缓存可能把已删除或无权访问的数据送进答案。T：我的首要目标是保持授权与用户意图，再决定可用性策略。A：我会将查询无结果、后端故障、权限拒绝、过期证据分开；低风险问答可明确提示记忆暂不可用，高风险写入或依赖当前授权的动作必须中止。若使用缓存，必须绑定 scope、版本和有效期，并再次检查删除与撤权状态，不能跨租户补数据。R：目前这些是部署策略要求而非完整生产降级能力；我可以证明本轮错误不再假装成空命中，但不能据此承诺任何错误情况下都无损继续。

#### F32：一个人做个人项目，还需要沙箱和权限隔离吗？

S：单人使用降低了用户数量，并没有消除模型误操作、外部内容注入和多个任务同时写文件的风险。T：我需要按动作风险决定隔离强度，而不是按人数决定是否授权。A：只读记忆查询绑定可信 scope；代码执行限制工作区、网络、资源和可用工具；删除、发布等操作要单独确认；并发工作使用隔离目录和明确合并责任。对未知工具输出只当数据，不允许其改变权限。R：MemOS 已有数据范围与治理测试，但不是代码执行沙箱；我不会把 PostgreSQL tenant 隔离说成容器安全。是否引入容器或沙箱服务，需要实际执行场景、威胁模型和资源测量来决定。

#### F33：为什么不能用更多 Agent 解决可靠性问题？

S：多 Agent 可以分工，但也增加上下文复制、并发冲突、重试副作用和协调成本。T：我首先要证明一个任务确实能被独立拆分，且不同分支的结果可验收、可合并。A：我会先建立单 Agent 或确定性工作流基线，限定模型只能提出动作，授权与状态转移由代码执行；只有存在独立工作和清晰输入输出时再并发。共享文件、共享记忆与外部写入要分别管理版本和操作身份。R：MemOS 的深度来自治理和可验证状态，不来自 Agent 数量；本轮没有新增调度基础设施，也没有宣称多 Agent 比单 Agent 更准确。社招回答应给出选择条件和代价，而非罗列角色名称。

证据与追问来源：N38、N88、N95–N97、N101–N114；本轮[Waku 回归代码](https://github.com/Zhi-Xiang-Guo/waku-agent/blob/dbcda82615506db89f07d3187d64ba4c7032800a/evals/deterministic/test_memos_fact_store.py)。本主题通过线：能画提交点、区分真空命中/失败/未知结果，并现场解释 UUID 反例；红线：把 update 说成原子、把旧 live 结果挂到新提交。

## 主题七：记忆质量、上下文与新未见评测

### Q24：怎样防止记忆越积越多，却让 Agent 越来越差？

S：9 月社招面经直接问“重启后问题消失”这种相关性案例会不会污染知识库；MemOS 自己的冻结测试也暴露了政策过严导致零接受。T：我要同时控制错误写入与漏掉有价值事实，不能只追求存得多或拒绝得多。A：我把来源、事实、置信度、有效时间与适用范围分开，保留版本和证据，让 LLM 提案而确定性代码决定授权与状态；评测时分开统计候选、接受、正确谱系、检索命中、上下文入选和最终答案，不把空输出自动算安全成功。R：当前有工程治理证据，但原冻结结果仍是 MemOS 0/30、三种基线各21/30；policy-v3 的 DEV 3/3 只是修复方向信号。下一步是新未见样本和真实跨会话任务，不是把旧分数改掉。

#### F34：成功轨迹能直接沉淀成 Skill 吗？

S：一次操作后故障消失，可能是环境自行恢复，而不是这一步操作有效。T：我需要区分观察、根因假说、经过验证的规则和可执行程序。A：我会保存现象、环境版本、动作、前后状态、证据和验证方法，将未经证实的处置标为暂时规避；只有重复验证、边界明确且通过测试的流程才进入受版本管理的 Skill，风险动作仍需执行前授权。R：MemOS 当前能表达来源与版本，但没有实现自动因果发现或自动发布 Skill。我会把案例库作为可审查证据，不把用户点赞或模型高置信度当作因果证明，也不会照搬面经参考答案中的自动合并阈值。

#### F35：规则闸门便宜，是不是越严格越好？

S：关键词规则可以减少提取调用，但隐式偏好和不同表达方式可能被漏掉；MemOS 的负结果说明保守政策也可能让系统失去实用性。T：我要同时量化写入精确率、漏记率、治理队列压力与成本，而不是只优化一个指标。A：我会在开发集区分明确记忆命令、隐式稳定事实、一次性操作与不可信内容，再检查规则漏掉了哪些；对灰区保留 REVIEW 和可追溯原因，必要时设计受授权的显式 remember 路径。R：这仍需要新的对照实验，不能声称规则可免费过滤百分之九十，也不能用放开全部权限来追求召回。成本低与记忆正确是两项独立要求。

#### F36：长窗口足够大，为什么还需要 Memory？

S：长窗口增加可输入内容，但不会自动解决授权、过期事实、冲突、来源和跨会话选择。T：我要回答的是哪些信息此时适用，而不是最多能塞多少 token。A：我的设计把短期执行状态、可重建摘要、持久事实与来源分离；当前任务约束优先保留，长期事实按可信 scope 和时间检索，过期或已删除内容不能因为历史里存在就复活。必要时从原证据按需读取，而非让摘要成为唯一真相。R：MemOS 针对的是这套治理边界，是否提升最终效果仍要与 full-context 基线比较。现有冻结基线表现更好，因此不能说长上下文必然不行或 Memory 必然占优。

#### F37：摘要把早期关键要求压没了，怎么发现？

S：滚动摘要可能保留最近对话，却遗失早期禁止事项、验收条件或未决问题。T：我要让压缩损失可检测、可恢复，而不是只写一句“请保留重要信息”。A：我会建立结构化保留字段：任务目标、约束、确认决策、来源引用、未完成事项和工具状态；压缩前后用专门的问题检查这些字段，失败时回读原始证据。对长期事实走独立写入政策，不能在摘要里悄悄提高来源可信度。R：本项目当前 context assembler 做预算与证据包装，并不等于完成了 Waku 全部摘要质量控制。这里的复原与损失评测属于待落地方案，要单独建 DEV 用例后再验证未见任务。

#### F38：为什么要同时看候选命中和 selectedVersionIds？

S：检索器可能找到正确版本，但它被重排或 token 预算丢掉，回答模型实际没有看到。T：我要把问题定位到检索、选择还是生成，避免一个总召回率掩盖信息丢失。A：我会记录合法候选集合、融合排序、最终入选 ID 和答案引用；对于多证据题，分别判断任一 gold 是否命中、全部 gold 是否齐全，再看引用是否真能支持答案。R：MemOS 已把 selectedVersionIds 作为消费边界，基准也修复过引用只应来自可见证据的问题。但 ID 合法仍不代表推理正确；我不会把报告里历史命名为 recall_at_k 的 any-hit 当成标准召回率，也不会只看候选列表宣布检索成功。

#### F39：BM25、词项检索和 RRF 是同一层的东西吗？

S：面经常把 BM25、向量和 RRF 连着讲，容易让候选人以为名字组合就是完整实现。T：我需要先分清各通道的相关性评分与跨通道排名融合。A：BM25 是一种词项相关性打分方法；向量通道处理语义相似；RRF 根据各通道名次合并，避免直接相加不同量纲的原始分数。放回 MemOS，我会如实说当前使用项目已有 lexical 通道，不能未核对实现就改口称为 BM25。R：RRF 不给出事实真实性概率，也不保证总优于单通道。是否更换词法评分、是否加权，应由真实查询分布与消融结果决定，而不是为对齐 JD 添加一个名称。

#### F40：同名 embedding 模型重新部署了，旧向量还能用吗？

S：模型名称不变，不代表权重、维度、tokenizer 或归一化方式没有变化；混用向量可能让召回失效。T：我要识别可比较的表示空间，并避免旧任务把旧表示写回当前代次。A：我会用完整 embedding profile 和 generation 区分构建，查询与投影匹配同一身份，重建从 authority 读取并校验后再切换；A→B→A 也不能只按名字判断已经最新。R：项目已有代次和维护式重建边界，但不宣称零停机在线迁移，也不宣称自动修好同代次任意损坏。这个回答要落到 ADR0006 和相关测试，而不是以“模型版本有管理”一句带过。

#### F41：你看过冻结 test 了，还怎样做独立评测？

S：修复过程中我已经分析过冻结样本，继续对这些标签调参会污染泛化判断。T：我要保留旧负结果，同时建立新的、预先定义范围的未见评测。A：先固定场景分层、去重与泄漏检查、模型身份、预算、评价规则和退出标准；由独立审核者或封存流程准备新样本，调参只用 DEV，评测前冻结代码与清单。运行失败、拒答、空答案和缺用量均单列，不能删除难例。R：本轮完成的是研究与协议设计，没有执行新 heldout；旧 test 仍保留原结果。所谓独立复建只验证报告包机械一致性，不等于独立重现模型输出，更不等于标注天然正确。

证据与追问来源：N33、N53、N69、N101、N103、N116–N119；[冻结结果](../benchmark/results.md)、[ADR0006](../adr/0006-projection-identity-reconciliation.md)。通过线：能逐层解释零接受与零得分，并设计反例；红线：把别人的参考答案当自己的实现，把 DEV 提升或命中率当泛化证明。

## 主题八：岗位定位、传统后端与个人项目取舍

### Q25：根据社招和 JD，MemOS 要继续做深，还是换项目？

S：招聘名称都写 Agent，但实际可能是 Java 业务后端、全栈交付、编排平台、售前方案或模型算法，要求并不相同。T：我需要让个人项目证明目标岗位最重要的能力，而不是补齐所有公司用过的技术栈。A：结合本轮自述面经与官方 JD，我把 MemOS 定位为 Java/AI 应用后端的深度证据项目：主讲可信写入、并发状态、检索治理、失败复盘和消费者合同；面纯后端时保留真实业务经历为主，面 Agent 应用时补跨会话任务与评测结果。R：当前判断是保留但限制投入，不重开一个同质聊天/RAG 项目，也不直接扩到图数据库、RL 或推理集群。若真实任务仍不能证明需要这层记忆，就降级为治理组件，不用架构复杂度替代业务价值。

#### F42：为什么不把 Java 全换成 Python 迎合 Agent 岗？

S：官方 JD 同时出现 Java/Python/Go，部分岗位又有特定语言和领域经验要求。T：我要匹配具体岗位职责，而不是相信一种语言适合所有 Agent 系统。A：Java 负责 MemOS 的确定性业务规则、事务和 API，Python 用于 benchmark 与 Waku 消费，形成可以实际展示的跨语言边界。我会补 Python 的异步、类型、测试与包装能力，但保留已验证的 Java 核心；只有实际依赖生态或部署瓶颈迫使调整时才评估替换。R：双语言本身不是优势证明，接口与故障合同才是；也不能推断市场上百分之多少公司采用同样架构。投递时按 JD 的主语言与工作内容决定叙事顺序。

#### F43：Java 后端岗位会怎样从这个项目追问到数据库？

S：面试官看到可靠写入和并发更新，会继续问事务边界、锁竞争、索引与慢查询，而不会只停留在 Outbox 名词。T：我要能把领域约束映射到实际 SQL 和数据库行为。A：我会沿 source/outbox 唯一键、owner/fence 条件更新和版本 If-Match 说明并发冲突如何检测，再用执行计划与数据分布分析查询，而不是宣称加索引一定更快。模型调用放到长事务外，减少锁和连接占用。R：这些能支持数据库工程讨论，但 MemOS 当前没有生产大流量证明；涉及 MySQL 的 MVCC、binlog 等题目，要作为迁移知识单独回答，不能把 PostgreSQL 项目说成已实战所有数据库机制。

#### F44：线程池参数怎么定，为什么不是“CPU核数乘二”？

S：AI 请求既有 CPU 工作，又可能长时间等待模型和数据库；简单增加线程可能耗尽连接和下游配额。T：我要找到系统真正的容量限制，并让过载行为可控。A：我会先拆队列等待、CPU、I/O、provider 延迟与连接占用，再根据并发目标、下游并行上限、内存预算和超时确定有界队列及拒绝策略，用负载阶梯验证尾延迟和错误率。虚拟线程也不创造更多数据库连接或模型额度。R：这是容量设计方法，不是本项目已有的最佳参数；没有代表性压测，就不在简历写某个 QPS。面试时我可以给出需要采集的指标和实验步骤，而不是背一个通用公式。

#### F45：为什么不加 Redis、Kafka、Elasticsearch，把后端深度补齐？

S：这些组件各有价值，但个人项目多一个组件就多一套同步、故障、部署和运维责任。T：我要用最小系统证明关键约束，而不是靠组件数量展示经验。A：当前 PostgreSQL 提供 authority、事务与持久任务，已有投影可以重建；我会先测出查询热点、队列吞吐或搜索质量不足，再提出具体组件的收益假设和替代方案，并用 ADR 记录引入门槛。R：在没有测量需求前，我不为 JD 名词新增基础设施。传统后端知识可以用隔离练习学习，但只有真正使用并验证的组件才写成项目实现；否则面试一追问集群故障与一致性就会暴露叙事不实。

#### F46：为什么不能用现成框架替代你整个项目？

S：框架能提供消息、工具与存储接口，这确实减少重复工程。T：我需要证明自研部分解决了框架接口之外的明确问题，而不是以“更灵活”作为万能理由。A：MemOS 的重点是候选来源上限、确定性状态转移、版本与删除生命周期、投影代次和可审计评测；我会逐项比较框架当前的真实能力，只把缺口或不同产品约束留在自己这边。若现成方案已经满足需求，我会接入而不是重复实现。R：这只是本项目的研究与工程价值定位，不是声称全面优于某个框架。冻结质量负结果仍限制产品结论，框架不存在某能力也必须在明确版本和源码范围内核验。

#### F47：怎么证明 AI Coding 的个人贡献，而不是背生成的答案？

S：代码由 AI 辅助生成后，提交数量或代码行数不能说明我理解了设计。T：我要证明自己能定义问题、发现错误、选择取舍并承担验收责任。A：我会展示一个具体红绿案例：先读 FactStore 合同，沿工具层找到错误的整数假设，用反例让测试失败，再解释最小修改和仍未解决的边界；面试现场独立改一个小功能并补测试，不把整个仓库实现都归为纯手写。R：本轮留下了可审查代码与门禁证据，但用户是否独立掌握仍需复练确认。若我不能解释为什么断言有效、为什么选这个边界，就不把这一点写成可熟练应答的核心亮点。

#### F48：个人项目没有线上用户，结果项 R 怎么写？

S：STAR 的 Result 很容易被误解为必须填写增长、收益或性能百分比。T：我要给出真实可观察结果，同时保持项目身份是个人工程验证。A：我会写明修复前哪条合同失败、修复后哪些测试通过，提供提交、复现步骤、原始包和剩余风险；对于尚未上线的功能，结果可以是排除一个错误假设、发现负结果并缩小下一步范围。R：这样能展示工程判断，却不能替代生产经验；没有用户、业务转化或独立未见提升，就明确没有。也不能把别人项目的成功率、文章中的收益数字或本地测试数量包装成自己的业务效果。

#### F49：你会怎样验证一个真实跨会话任务？

S：记住一句偏好再查到它，只证明存取，不证明 Agent 完成任务时真的受益。T：我会选择“跨会话遵守用户约束并正确接受纠正”的小任务，避免先扩大场景。A：分别运行无记忆、简单全文/摘要基线和 MemOS，固定模型、输入、预算与验收规则；首会话给约束，后续会话给任务，再插入纠正、冲突、另一租户和删除，核对最终产物而不是只看召回。记录失败、人工介入、耗时和含重试成本。R：本轮未执行这个新实验，因此不能写已有提升；它是下一优先级的实际验收入口。如果复杂记忆不能提供相对简单基线的价值，就缩减项目定位。

#### F50：入职前反问什么，才能避免“岗位名字对、工作内容不对”？

S：自述面经里出现过投 Agent 实际面传统后端、投研发实际走售后支持的情况。T：我需要确认岗位的真实产出和团队分工，而不是仅凭标题决定准备方向。A：我会询问前三个月交付什么、Java/Python/前端的比例、模型训练是否由独立算法团队承担、现有 Agent 是产品还是内部工具、谁定义评测和生产故障责任、是否需要值班与客户交付；再针对对方最重要的一条需求展示对应证据。R：这些答案会决定简历主次和学习优先级，不能保证录用或某种薪资。个人项目只能证明可迁移能力，不能替代 JD 硬性年限、学历、领域和生产责任要求。

证据与追问来源：N02、N78、N95–N101、N104、N110、N120；本轮 RJD01–RJD32。通过线：两分钟分别面向 Java 后端与 Agent 应用讲同一项目，并主动说明未证实项；红线：按 BOSS 摘要推断完整任职要求，按便利样本推断市场占比或录用概率。
