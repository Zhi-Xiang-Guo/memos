# 10 一年项目路线与社招表达

## 本章导学

**学习目标**：把前九章变成持续一年的可执行工程计划和可信面试资产，避免项目数量多、机制浅、数字无证据。

**前置知识**：至少通读第 00-09 章；建议直接结合工作区现有 MemOS 项目推进。

**读完产出**：季度 OKR、每周闭环、证据账本、作品集 release checklist、3/10/30 分钟讲法和按目标公司调整的项目入口。

## 1. 最终项目定位

不要把项目讲成：

> 我学习了 mem0、LangChain、pgvector，做了一个能记住用户的聊天机器人。

应该讲成：

> 我观察到跨会话 Agent 会把噪声、过时事实和外部恶意指令变成长期状态，因此研究主流 memory 产品、论文和源码，构建一套有版本/时间/溯源/权限的权威记忆层与可重建混合检索投影，并用故障注入、删除/隔离测试和等预算 benchmark 证明它在哪些边界内优于 history、summary 和 vector-only。

这个叙事体现：发现问题、自主研究、下钻原理、工程闭环、证据意识。

## 2. 一年能力目标

一年后应能独立完成：

1. **问题定义**：用失败案例解释 memory 不是 embedding + vector DB。
2. **源码研究**：固定 commit/版本，区分 paper、OSS、hosted platform 和 deprecated API。
3. **系统设计**：写/manage/read、authority/projection、同步/异步、一致性/失败语义。
4. **实现**：版本时序状态机、outbox/幂等、混合检索、context builder、删除状态机。
5. **测试**：单元、数据库、并发、故障、隔离、隐私、重放、projection rebuild。
6. **实验**：baseline、control、ablation、run manifest、置信区间、成本。
7. **表达**：3/10/30 分钟讲法；能连续回答五层为什么并承认未验证边界。

## 3. 学习闭环

每个主题走五步：

```text
观察失败 -> 阅读一手资料 -> 建立机制/不变量
-> 实现并攻击 -> 形成可复核证据
```

每周复盘：

```text
本周问题：
最小失败案例：
一手资料与固定版本：
关键不变量：
实现/测试：
故障/攻击结果：
确认事实 vs 假设：
trade-off：
没有证明什么：
三分钟讲法：
下周最小闭环：
```

## 4. 第 1-2 月：从 0 到可运行 MVP

### 学习

- LLM/context/history/RAG/memory 边界；
- semantic/episodic/procedural；
- Agent loop、tools、retrieval gate、consolidation；
- SQLite、FTS5、事务和基本数据模型。

### 实现

- `source_event`、`fact`、`episode` 表；
- `MEMORY.md` 人类可读镜像；
- FTS5 检索和规则/小模型 retrieval gate；
- 每 N turns consolidation，失败不丢 source；
- basic trace：gate、retrieval、tool、tokens、latency。

### 测试

- 重启后跨会话记忆；
- exact/关键词；
- 未达到 N turns 不 consolidation；
- consolidation 失败后可重试；
- 两个 user 数据隔离。

### 输出

- 一张 Agent run 图；
- 一篇“为什么没先用向量库”的 ADR；
- 3 分钟 MVP demo。

## 5. 第 3-4 月：向量与混合召回

### 学习

- embedding、cosine、chunking、HNSW/IVF；
- PostgreSQL FTS、pgvector；
- RRF、cross-encoder、query rewrite；
- Recall@K、MRR、Stale@K、ablation。

### 实现

- PostgreSQL authority + pgvector projection；
- projection generation/model metadata；
- lexical/vector/entity/temporal 独立候选；
- RRF + deadline reranker fallback；
- token-budgeted context builder。

### 实验

- 英文记录、中文提问；
- exact ID/金额 vs paraphrase；
- vector-only、FTS-only、hybrid；
- 相同 answer model/evidence budget；
- queryable freshness 与 p95 latency。

### 输出

- 每个错误可定位到 candidate/fusion/context/answer；
- 一份可重跑的 retrieval artifact；
- 不写虚构“提升 30%”，只报告本地真实 run。

## 6. 第 5-6 月：受治理的写路径

### 学习

- structured extraction 与 strict decoder；
- trust、sensitivity、write policy；
- transactional outbox、at-least-once、lease/fencing、幂等；
- model proposal 与 deterministic authority 边界。

### 实现

- source + outbox 同事务；
- provider-neutral candidate schema；
- `REMEMBER/IGNORE/REVIEW` 与 reason codes；
- 外部/tool/assistant/direct-user 信任等级；
- secret reject/quarantine，无正文旁路泄漏；
- retry/dead/replay 和 effect ledger。

### 故障注入

- commit 前/后崩溃；
- provider 成功后进程死；
- lease 过期旧 worker 晚提交；
- 相同 idempotency key 不同 payload；
- 429/timeout/invalid JSON/oversize/deep JSON。

### 输出

- crash-window 时序图；
- 能回答“你能保证 exactly once 吗？”：不能保证 provider 只调用一次，保证逻辑 effect 幂等可见。

## 7. 第 7-8 月：版本化时序记忆

### 学习

- event/valid/transaction time；
- lineage、immutable version、append-only transition；
- cardinality、dedup、reinforce、supersede、coexist、conflict；
- optimistic locking 与 projection rebuild。

### 实现

- `memory_lineage/version/transition/source`；
- `CURRENT/HISTORICAL/CONFLICTED/INVALIDATED`；
- current/as-of/history/diff API；
- 7 点 -> 9 点；上海 -> 杭州；1000 星 -> 1300 星；
- 同 lineage 并发 correction。

### 验证

- 旧值不进入 current context；
- historical query 仍可解释；
- late event 不按 created_at 误判 current；
- projection 全删后重建等价；
- embedding similarity 只能提候选，不能直接 supersede。

### 输出

- 状态机和 bitemporal 时间图；
- 面试亮点从“做了向量检索”升级为“实现可审计事实演化”。

## 8. 第 9 月：Graph 与产品对照实验

### 学习

- entity resolution、ontology、typed edge、temporal graph；
- Graph RAG、multi-hop、图+向量；
- mem0、LangMem、Zep/Graphiti 的真实产品/库边界。

### 实验

- 运行统一晚宴数据；
- SQLite、pgvector、mem0、LangMem、Zep、control；
- 记录 said vs kept、state、edge validity、readiness；
- graph on/off 或自建 graph projection ablation。

### 决策

只有 multi-hop/temporal case 有可测收益才保留图。否则把“延后 Graph”写成基于证据的工程判断，这比技术堆叠更强。

## 9. 第 10 月：隐私、安全、删除

### 学习与威胁模型

- prompt injection -> persistent memory poisoning；
- cross-tenant leakage；
- PII/secret 写入；
- delete 后 projection/job resurrect；
- procedural memory 越权。

### 实现

- scope/ACL 硬过滤；
- retrieved memory 作为 untrusted data；
- deletion state machine + receipt；
- authority/vector/FTS/graph/cache/job/trace 全覆盖；
- deletion epoch/resurrection guard；
- procedural write capability 与人工批准。

### 输出

- threat model；
- cross-tenant、poison、deletion race 测试；
- 对备份保留边界的诚实说明。

## 10. 第 11 月：正式 Benchmark 与优化

### 数据集

中英双语、多 session，含 simple recall、preference、update、temporal、conflict、multi-hop、abstention、noise、privacy、poison。

### Baseline

full history、rolling summary、raw-turn vector、managed memory、no-memory control。

### 纪律

- train/dev/test 按故事族隔离；
- dev 调参、test 一次冻结 campaign；
- manifest 固定 commit/model/prompt/config/hash；
- 模型配置重复运行并报告 CI；
- 原始失败保留；
- 优化只针对测出的瓶颈。

### 输出

- generated/verified results；
- quality/latency/token/cost/storage trade-off；
- component ablation；
- limits 与未解决问题。

## 11. 第 12 月：作品集与面试

### 仓库验收

- clean clone 可无付费 API build/test/smoke；
- 固定 fake + 可选 live adapter；
- README 五分钟说清问题、架构、运行、状态；
- 每项 claim 可定位到 test/run/commit；
- 设计图、failure timeline、benchmark artifact 完整；
- `DONE/DOING/NOT RUN/UPSTREAM-REPORTED` 清楚。

### 3 分钟讲法

`问题 -> 关键反例 -> 架构 -> 最难机制 -> 实验证据 -> 边界`

### 10 分钟讲法

增加：竞品源码发现、架构演进、失败窗口、时间状态机、baseline/ablation。

### 30 分钟系统设计

从 SLO/规模/风险开始，推导 authority、outbox、projection、hybrid、delete、observability 和 scale triggers。

## 12. 简历四句结构

1. **问题**：跨会话 Agent 的噪声、过时事实、敏感内容会放大为长期风险。
2. **责任**：独立完成研究、架构、写/读/治理路径和可复现实验。
3. **机制**：版本时序权威、幂等异步写、混合召回/上下文策略、删除/隔离。
4. **证据**：真实测试/benchmark 的指标和边界；每个数字可回到 artifact。

未有 benchmark 前的无数字示例：

> 设计并实现面向长运行 Agent 的版本化记忆基础设施，将 LLM 语义提取与确定性权限/敏感/时间状态机解耦；以 PostgreSQL 为权威、FTS/pgvector 为可重建投影，通过 outbox、幂等 ledger 和 fencing 处理异步重试，并覆盖跨租户、过时事实、删除复活与投影重建测试。

有真实数据后再补：数据集规模、Recall@K/Stale@K、p95、token/cost、故障测试数；绝不预填数字。

## 13. 针对公司的“最对”项目表达

项目事实不变，入口随业务风险变化：

| 公司方向 | 重点 | 证据 |
|---|---|---|
| 金融/支付 | 幂等、审计、敏感、删除、历史真值 | fault suite、scope FK、deletion receipt |
| 电商/推荐 | 多租户、混合召回、ablation、成本 | Recall@K、latency、equal-budget baseline |
| 游戏/实时 Agent | freshness、deadline、降级 | watermark、timeout fallback、p95/p99 |
| Infra/平台 | 模块边界、provider ports、重建与运维 | architecture tests、replay/rebuild |
| AI Agent | write quality、temporal、poison、安全 context | policy/temporal/attack benchmark |

面前准备一页纸：对方产品 memory 失败会造成什么、项目哪三个机制最相关、两个 trade-off 如何变化、哪个能力尚未验证、下一步怎么测。

## 14. 高频深挖问题

回答固定结构：`问题 -> 失败反例 -> 设计 -> 保证 -> 代价 -> 证据 -> 未解决边界`。

- 为什么 vector DB 不是 source of truth？
- confidence 0.99 为什么不能直接写？
- source ID、idempotency key、semantic job key 为什么不同？
- old worker 晚提交如何挡住？
- valid time 与 transaction time 有何区别？
- embedding 为什么不能决定 supersede？
- lexical/entity 为什么不能只重排 vector TopK？
- reranker 超时/返回非法 ID 怎么办？
- 删除 PostgreSQL 行为什么不算完成？
- full history 和 memory 如何公平比较？
- deterministic fixture 通过为什么不是质量提升？
- 为什么暂时没用 Kafka/Graph DB？什么数据会触发引入？

## 15. 常见失败

- 一年都在“继续学习”，没有月度可运行产物。
- 堆 mem0/Zep/LangChain API，却无法解释 manager/store/retrieval 的维度差异。
- 项目很多，每个只有 README 和 Demo。
- 未跑 benchmark 却写提升比例/QPS。
- 只测 happy path，不测更新、越权、删除和重试。
- 把所有复杂基础设施都加上，反而无法说明一致性。
- 面试只讲技术名词，不从具体失败和权衡开始。

一个能被连续追问 30 分钟、每个结论有证据的项目，比五个只能讲 API 的项目更强。

## 16. 四个季度的硬里程碑

| 季度 | 系统能力 | 必须存在的证据 | 不能提前声称 |
|---|---|---|---|
| Q1 | SQLite MVP、gate、consolidation、trace | restart/隔离/失败重试测试、架构图 | 生产级、语义召回强 |
| Q2 | 受治理异步写、版本时序 authority | crash suite、policy fixtures、current/as-of API | exactly-once provider、完整隐私 |
| Q3 | hybrid retrieval、context、安全删除 | retrieval ablation、scope/poison/delete tests | 图提升、规模性能 |
| Q4 | 产品对照、正式 benchmark、作品集 | immutable runs、results、limits、demo | 未运行的提升率/QPS |

季度结束必须做一次 scope review：删除无证据的复杂组件，冻结一个可演示 release，而不是永远处在大重构中。

## 17. 每周执行系统

推荐每周 12-15 小时：

```text
2h  问题与一手资料
2h  设计/状态机/测试案例
6h  实现
2h  故障与安全测试
1h  artifact、文档与三分钟复述
```

每周只承诺一个可闭环问题，例如“旧 worker 不得覆盖新 owner”，而不是“学习分布式系统”。完成定义：代码、正反测试、运行证据、文档、限制全部落地。

## 18. Evidence Ledger

维护一张只记录真实证据的表：

| Claim ID | 声明 | 状态 | 代码/测试 | Run artifact | 限制 | 可用于简历 |
|---|---|---|---|---|---|---|
| C-001 | duplicate delivery 只产生一份 logical effect | VERIFIED | test path | run ID | 单 DB 边界 | 是 |
| C-002 | hybrid 优于 vector-only | NOT RUN | harness only | none | 无结果 | 否 |
| C-003 | graph 改善 multi-hop | HYPOTHESIS | none | none | 待 Q3 | 否 |

README、简历和面试材料只从 ledger 中抽取 `VERIFIED`；`UPSTREAM-REPORTED` 和 `HYPOTHESIS` 可以作为研究背景，不写成自己的成果。

## 19. 项目范围控制

### 核心必须做深

- governed write path；
- versioned temporal authority；
- rebuildable lexical/vector projections；
- hybrid retrieval/context policy；
- isolation/deletion/poison defense；
- reproducible evaluation。

### 延后直到证据触发

- Kafka、Redis、OpenSearch、专用 Vector DB；
- 多地区 active-active；
- 自研图数据库/GNN；
- learned policy/RL；
- Web UI 大量视觉功能。

社招亮点来自清晰不变量和困难 case，不来自基础设施数量。

## 20. 3/10/30 分钟讲稿骨架

### 3 分钟

```text
30s  真实问题与最小反例（7 点改 9 点）
45s  研究发现：vector search 不拥有 truth lifecycle
60s  架构：authority + async write + rebuildable hybrid projections
30s  最难机制：版本/时序/删除复活
15s  证据与边界
```

### 10 分钟

加入从 SQLite/vector-only 演进、竞品固定版本实验、outbox/fencing、Stale@K 和一个失败样本。不要逐模块念技术栈。

### 30 分钟

让面试官选择深挖：写路径、时序、检索、安全、benchmark。每条都能走 `反例 -> 不变量 -> 实现 -> 故障 -> 证据 -> trade-off`。

## 21. 简历数字的审计规则

每个数字必须回答：

- 分母是什么，样本多少？
- 与哪个 baseline、相同什么预算？
- commit/config/model/dataset 是什么？
- 冷/热、p95/p99、失败样本如何处理？
- 结果是否可重新生成？
- 是本地实测、vendor 报告还是估算？

如果无法回答，删掉数字，改写为已验证机制。没有数字的严谨项目描述优于虚构精确度。

## 22. 模拟拷打方法

每周随机抽一个决策，连续追问五层“为什么”：

```text
为什么用 outbox？
为什么 source 与 intent 必须同事务？
为什么 at-least-once 会重复 effect？
为什么 idempotency key 不能解决旧 lease？
为什么需要 fencing，测试如何证明？
```

若回答停在“最佳实践/框架就是这样”，回到源码、时序图和故障实验。把答不出的点加入 backlog，不临场编造。

## 23. 最终分级验收

### 合格

能运行、能跨会话、能搜索、能解释基本架构。

### 良好

有版本/时序、hybrid、trace、隔离和分层测试，能定位失败。

### 社招亮点

有并发/故障/删除/投毒、可重建投影、正式 baseline/ablation、真实 cost/latency/quality 结果。

### 资深讨论水平

能根据业务风险和规模改变 consistency、store、ranking、retention；能指出系统不保证什么，提出下一步可证伪实验，而不是给出万能架构。

## 24. 本章验收

- 一年计划每季度有可运行 release，不只是学习清单。
- Evidence Ledger 能阻止未验证 claim 进入简历。
- 能在 3 分钟内讲清问题、机制、证据和边界。
- 能被追问五层为什么并落到代码/测试/run。
- 能针对公司换叙事入口但不改变项目事实。
