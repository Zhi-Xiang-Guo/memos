# 03 五层存储阶梯

## 本章导学

**学习目标**：掌握从文件到时序图的能力增量与复杂度增量，能基于数据规模、查询类型、一致性和团队运维能力选择最小充分方案。

**前置知识**：第 00-02 章；建议知道 SQL、倒排索引和 API 的基本概念。

**读完产出**：一份带升级触发器、退出方案、迁移步骤和 TCO 的存储 ADR，而不是“技术越新越好”的选型表。

## 1. 为什么要按阶梯学习

存储方案不是“越高级越好”，而是随规模和查询结构逐步增加能力。每升一级，都引入新的成本、一致性边界和故障模式。

```text
纯文本 -> SQLite/FTS -> Vector -> Managed Memory -> Temporal Graph
  透明       结构化       语义        生命周期          关系+时间
```

判断标准不是 star 数，而是：数据量、问题类型、更新频率、关系密度、权限/审计要求、运维预算。

## 2. 第一层：纯文本

### 解决什么

少量个人记忆、可人工编辑的 persona、规则和项目笔记。几十条事实全部注入上下文可能比检索更便宜、更可靠。

### 常见文件

- `SOUL.md`：身份、价值观、长期行为偏好。
- `SKILL.md`：程序性记忆，描述某类任务如何做及可用工具。
- `MEMORY.md`：长期事实、重要人物、项目状态的人工可读视图。

### 第一性原理

当整个记忆集合小于可接受 token 预算时，检索层只会增加漏召回、延迟和复杂度。全量读取具有 recall=1 的优势。

### 最小实现

```text
memory/
  SOUL.md
  MEMORY.md
  skills/
    deploy/SKILL.md
```

启动时加载 SOUL；按任务匹配 Skill；需要个人信息时读取 MEMORY。

### 深层问题

- 多进程同时改文件会覆盖；需要原子写/锁。
- 文本没有稳定 ID、版本和 schema，精确修正困难。
- 反复让 LLM 重写整个文件会发生 summary drift。
- 纯文本仍需 provenance，否则无法知道某句来自哪里。

### 何时升级

事实达到数百条、需要按字段/时间查询、多人并发、需要审计或更新一条而不是重写全文。

## 3. 第二层：SQLite `state.db` + FTS5

### 解决什么

本地单用户 Agent 的结构化持久化、事务和关键词检索。零额外服务，适合教学、桌面 Agent 与 MVP。

### 推荐最小表

```sql
CREATE TABLE source_event (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL,
  role TEXT NOT NULL,
  content TEXT NOT NULL,
  occurred_at TEXT,
  created_at TEXT NOT NULL
);

CREATE TABLE memory (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL,
  type TEXT NOT NULL,
  subject TEXT,
  predicate TEXT,
  content TEXT NOT NULL,
  status TEXT NOT NULL,
  valid_from TEXT,
  valid_to TEXT,
  source_event_id TEXT,
  created_at TEXT NOT NULL
);

CREATE VIRTUAL TABLE memory_fts USING fts5(
  content, subject, predicate, content='memory', content_rowid='rowid'
);
```

生产实现应增加 scope、version、transition、sensitivity 和约束；这里仅展示机制。

### 关键词检索为什么有价值

BM25/FTS 对 `Paul Graham`、订单号、金额、库名和精确术语往往胜过 embedding。它可解释、便宜、没有模型版本漂移。

### MEMORY.md 镜像模式

可让 `state.db` 做权威状态，每次变更后生成只读 `MEMORY.md`：

```text
state.db (source of truth) -> deterministic renderer -> MEMORY.md (human view)
```

不要让人和程序同时把镜像当权威，否则会产生双向同步冲突。

### 局限

- 跨语言/改写召回差。
- 写入者必须自己处理去重、冲突和 retire。
- 高并发、横向扩展与远程访问受限。

## 4. 第三层：向量索引 / Vector DB

### 解决什么

查询与记忆用词不同、跨语言、规模达到上千/百万片段时的语义候选召回。

### 数据结构

```text
id, text, embedding[], metadata, embedding_model, created_at
```

向量只应是 projection：

```text
authority row --embed(model/version)--> vector projection
```

升级 embedding 模型时创建新 generation，验证后切换 active head；不要原地混用不同维度或分布。

### 技术选择

- **pgvector/Supabase**：与 PostgreSQL 事务和过滤共处，MVP 优先。
- **Weaviate/Qdrant/Milvus**：需要更专门的 ANN、过滤、规模和运维能力时。
- **Pinecone**：托管优先，减少运维但增加供应商边界。
- **Chroma/FAISS**：原型与本地实验；需自行补持久化/服务治理。

### 不解决什么

Vector DB 不知道旧事实失效、来源是否可信、是否越权、何时有效，也不自动完成删除传播。它是候选生成器，不是 Memory Manager。

### 何时升级

需要自动决定记什么、归一化事实、处理增删改；或需要实体关系、多跳和时间有效性。

## 5. 第四层：mem0 的 row memory 与 graph memory

### 解决什么

mem0 把“形成记忆”产品化：输入消息后，系统提取、改写、合并或忽略，提供搜索与生命周期能力，而不是要求调用方直接写原句。

### Row memory 心智模型

```text
messages -> extractor/manager -> atomic memories -> search
```

重要现象：你说的句子和最终存的 memory 可能不同；这正是产品价值，也意味着需要审计和 provenance。

### Graph memory 当前边界

截至 2026-08-29 的平台文档：Graph Memory 为内建能力，自动抽取实体节点；共享实体连接多条 memories；查询时实体匹配对候选加权，并与 vector、BM25 合成一个 score。当前平台文档明确它主要是实体共现连接，并不等同于任意 typed relationship knowledge graph。

这也说明“mem0 只是 row store”已不是完整描述；但本地固定的 `mem0ai 2.0.17` 实验测的是当时默认 API 行为，不能把实验结论无限外推到当前平台。

### 风险与验证点

- `add` 返回与可查询可能不是同一时刻，必须测 freshness。
- lifecycle 字段可能不在列表/搜索结果的默认视图中。
- superseded 事实仍可能被相似搜索返回；消费端必须读取状态。
- 自动推断可能补出用户没说的年份或实体，需要区分事实与模型推断。

## 6. 第五层：Zep / Graphiti 时序图记忆

### 解决什么

当关系和事实随时间变化，Zep/Graphiti 使用实体、关系边和 episodes 构建 temporal knowledge graph。旧事实可以保留为历史，并通过有效时间表达何时停止为真。

### 核心模型

```text
Episode: 一段输入证据
Entity node: 人/组织/对象
Fact edge: 带语义的关系
Validity: valid_from / valid_to
```

“Elon 19:00 到”改为 21:00：旧边不必删除，而是设置 `valid_to=change_time`；新边从变更时刻生效。

### 第一性原理

关系查询是 traversal，不是文本相似度；历史真值是 interval 问题，不是 `created_at DESC LIMIT 1`。图和时间一起解决“谁与谁以什么关系、在何时成立”。

### 代价

- 实体解析/消歧错误会污染图。
- ontology/schema 会影响可学内容。
- ingestion 常为异步，`accepted/processed/queryable` 可能是不同事件。
- 图搜索仍可能返回历史/无效边；调用方必须使用有效性字段。
- 图与关系权威存储若分离，会出现 dual-write、删除和重建复杂度。

### 何时是杀鸡用牛刀

- 只有单用户几十条独立偏好；
- 问题主要是精确名字/简单事实；
- 不需要多跳或历史有效期；
- 团队无法承担实体质量、图 schema 和运维。

## 7. LangMem：它是 Manager/Library，不是存储产品

LangMem 提供提取、更新、反思等记忆管理能力，并接入 LangGraph store。它本身不是一个必须使用的托管数据库；示例完全可以把 store 放在进程内 dict 中，因此进程退出即消失。

正确问法不是“LangMem 和 Pinecone 选哪个”，而是：

```text
manager: LangMem / custom / mem0
store: dict / PostgreSQL / vector DB / graph
```

它们可以组合，不在同一个比较维度。

## 8. 选型决策树

```text
记忆 <= 几十条且能全量注入？ -> Markdown
需要结构化/本地事务/精确词？ -> SQLite + FTS5
存在大量改写/跨语言/上千片段？ -> 加 vector
需要自动形成、去重、更新？ -> memory manager（自建/LangMem/mem0）
关系多跳且变化重要？ -> temporal graph（先做基准证明）
多租户、审计、删除、并发？ -> PostgreSQL 版本化 authority + 可重建投影
```

## 9. 技术选型面试答法

不要说“Zep 更高级”。应说：

> 初期事实量小、查询词稳定，因此用 SQLite FTS5 保持透明和零运维；跨语言测试暴露 recall 缺口后增加 pgvector，并保留 FTS 做 hybrid。关系型多跳用例在基准中占比低，图方案没有显著质量收益，因此暂缓，避免新增实体消歧和双写边界。事实更新由 PostgreSQL 版本状态机负责，向量只是可重建投影。

## 10. 容量不是只看条数

选型应估算：

```text
users * active_memories_per_user * versions_per_memory
* (row_bytes + vector_bytes + index_overhead + provenance_bytes)
```

例如一个 1536 维 float32 向量裸数据约 `1536 * 4 = 6144 bytes`，尚未包含 row、metadata、ANN 图和数据库开销。若每条 memory 还有多个 embedding generation，存储会成倍增长。实际容量必须通过 `pg_total_relation_size` 或对应产品统计测量，而不是只算向量数组。

查询负载也要拆：

- QPS 与并发用户；
- filter 选择性和每用户数据量；
- 写多还是读多；
- 更新/删除频率；
- cold/warm cache；
- TopK、rerank N、p95/p99 SLO；
- 单租户热点与数据地域要求。

百万总 rows 但每次严格过滤到单用户 100 条，与一个用户拥有百万 rows 是完全不同的索引问题。

## 11. 分层迁移，而不是一次重写

### Markdown -> SQLite

1. 为每条文本分配稳定 ID、type、source 和 created_at。
2. 导入 SQLite authority；保留原文件 hash/backup。
3. 从 DB 生成 deterministic `MEMORY.md`，做内容 diff。
4. 将写入口切到 DB，文件变只读 mirror。

### SQLite -> PostgreSQL + pgvector

1. 冻结 schema 和导出格式；
2. 迁移 authority rows 与 provenance，不先迁 embedding；
3. 在 PostgreSQL 重建 FTS；
4. 以固定 embedding spec 构建新 projection；
5. shadow query 对比结果后切读；
6. 保留回滚窗口，再停止旧写入。

### Row -> Graph projection

不要把关系图直接变成新的唯一 truth。先从 authority 生成 entity/edge projection，记录 edge -> memory version -> source 的链；graph 删除后能重建。只有图本身包含无法从 source 重建的人工业务知识时，才需要重新定义权威边界。

## 12. 供应商锁定检查表

选择托管 Memory/Vector/Graph 服务前确认：

- 是否能完整导出 raw memory、lifecycle、provenance、embedding spec 和 graph edge？
- 删除 user 是否同时删除 ontology、索引、日志和 derived state？
- 写入/搜索的异步 readiness 是否有正式状态？
- hosted 算法版本会不会静默变化？
- 自定义 embedding/region/encryption/retention 是否支持？
- 数据退出后能否在本地重建同等语义？
- 费用包含写入推理、存储、检索、图、rerank 和出口流量吗？

“API 兼容”不等于语义可移植；最难迁移的是 manager 对事实的改写和 lifecycle 状态。

## 13. TCO 与运维复杂度

```text
TCO = infra + model calls + storage/index
    + engineering + on-call + migration + compliance + lock-in
```

SQLite 的 infra 近乎为零，但并发、备份、远程访问由你承担；PostgreSQL 提供统一事务边界，但需要 migration、连接池和数据库运维；专用向量/图服务减轻部分算法运维，却新增网络、权限、账单和一致性边界。

选型 ADR 至少包含：需求、候选、决策、拒绝原因、可测假设、升级触发器、回退路径、数据退出方案。

## 14. 动手练习与验收

### 练习

为三个规模写 ADR：

1. 单用户 50 条偏好；
2. 10 万用户、每人 500 条中英记忆；
3. 研究组织关系、每条关系有历史有效期。

必须给出 authority、projection、检索、维护、SLO、迁移和删除方案。

### 本章验收

- 能解释每一层新增了什么能力和什么失败模式。
- 能区分 LangMem manager 与持久化 store。
- 能估算 vector 的数量级容量，但不把估算冒充实测。
- 能设计无停机或可回滚的分层迁移。
- 能用 benchmark trigger 决定是否引入图，而不是凭先进程度。
