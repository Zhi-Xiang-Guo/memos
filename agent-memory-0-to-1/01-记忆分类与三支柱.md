# 01 记忆分类与三支柱

## 本章导学

**学习目标**：用“功能类型”和“Shape/Find/Manage”两个正交坐标描述任意 Memory 系统，避免把认知标签、数据库和检索算法混为一谈。

**前置知识**：完成第 00 章，能区分持久状态与当前上下文。

**读完产出**：为一个事实写出完整 memory contract，说明它属于哪种功能类型、存成什么、如何召回、如何演化，以及谁可以使用。

## 1. 两个正交坐标系

理解 Agent Memory 最容易犯的错误，是把“记忆内容是什么”和“用什么技术保存”混成一件事。应该使用两个坐标系：

- **功能分类**：working、semantic、episodic、procedural。
- **系统三支柱**：shape、find、manage。

一条“用户喜欢深色主题”的语义记忆，可以存进 Markdown、SQLite、PostgreSQL、向量库或图；也可以用关键词、向量或结构化查询找到。内容类型不决定实现技术。

## 2. 功能分类：记的是什么

### 2.1 Working Memory：当前正在做什么

内容包括当前目标、计划、尚未解决的问题、最近工具结果、scratchpad。保留时间通常是一个 run 或一个任务。

适合：消息列表、状态对象、checkpoint、压缩摘要。

不适合：把所有 working state 永久写成用户画像，否则临时信息会污染长期状态。

### 2.2 Semantic Memory：长期事实是什么

内容包括用户偏好、人物/项目稳定属性、长期约束。

```text
User prefers concise Chinese answers.
Paul Graham owes the user 200 dollars.
```

需要：去重、实体/谓词识别、当前状态、可信度、来源、版本。

### 2.3 Episodic Memory：什么时候发生了什么

内容包括带时间和上下文的经历、会议、决策、失败轨迹。

```text
2026-08-29: At dinner, Jensen brought a bottle of chili oil.
```

需要：事件时间、顺序、参与者、来源和历史查询。情节记忆不是语义事实加一个 `created_at` 就够了。

### 2.4 Procedural Memory：以后应该怎么做

内容包括可复用工作流、工具用法、经验规则、Skills。

```text
When deploying this service, run migration verification before rollout.
```

程序性记忆能改变 Agent 行为，风险最大。来自网页或工具输出的“规则”不能自动升级成程序性记忆；通常需要可信来源、验证结果或人工批准。

### 2.5 其他常见标签

- **Profile memory**：语义记忆的用户画像视图。
- **Entity/relationship memory**：从语义/情节记忆派生的实体关系投影。
- **Task memory**：若存在可靠任务系统，任务状态应留在领域服务；Memory 只做辅助检索。
- **Parametric memory**：模型参数中的知识，不具备逐条来源、实时更新和精确删除能力。

## 3. Harness 回顾：三类长期记忆如何进入 Agent

典型 Harness 会把不同记忆装配成 working context：

```text
system/developer instructions
+ SOUL.md / standing preferences       <- 语义/行为边界
+ matched SKILL.md                     <- 程序性记忆
+ retrieved facts                      <- 语义记忆
+ retrieved episodes                   <- 情节记忆
+ recent conversation/tool results     <- 工作记忆
```

关键不是把所有内容拼起来，而是决定每一层的优先级、可信度、token 预算和冲突处理。

## 4. 支柱一：记忆是什么形态 Shape

| 形态 | 优点 | 主要风险 | 适用阶段 |
|---|---|---|---|
| 纯文本文件 | 透明、可编辑、零服务 | 并发、结构、检索、冲突弱 | 少量个人记忆 |
| 关系表 | 事务、约束、版本、权限强 | 需要 schema 与迁移 | 生产权威状态 |
| 向量 | 语义召回强 | 无法单独判断真值/时间 | 派生语义索引 |
| 稀疏/FTS | 名字、ID、关键词准确 | 同义改写弱 | 与向量互补 |
| 图 | 多跳关系、路径解释 | 实体消歧和维护昂贵 | 关系问题足够多时 |
| 参数 | 调用时无需检索 | 更新/删除/溯源困难 | 通用能力，不做用户事实 |

建议：**权威状态优先用关系模型；向量、FTS、图作为可重建投影。**

## 5. 支柱二：Agent 怎么找到 Find

### 5.1 什么都不做：全量放入上下文

几十条以内往往最好。简单、透明、没有召回遗漏。不要为了“用了 AI”过早上向量库。

### 5.2 关键词/FTS

适合名字、金额、产品名、ID、已知词汇。SQLite FTS5/PostgreSQL FTS 足够覆盖许多小型系统。

### 5.3 Vector RAG

适合改写、同义表达、跨语言语义。它把查询与记忆编码为向量，再找相近候选。

### 5.4 Hybrid Search

独立运行 lexical、vector、entity、temporal 召回，再用 RRF 或校准分数组合。生产系统通常比 vector-only 更稳。

### 5.5 Graph Traversal / Graph RAG

适合“谁和谁一起参加过什么”“通过哪些关系连接”这类多跳问题。关系问题少时，图的成本可能远高于收益。

### 5.6 Retrieval Gate

先判断当前问题是否需要个人记忆：

```text
2 + 2 = ?                 -> 不检索
我下次和 Alex 几点见？   -> 检索
```

Gate 可以是规则、小模型或二者结合。需评估假阴性：如果 gate 说“不需要”但其实需要，后面再强的检索也无用。

## 6. 支柱三：怎么维护 Manage

一个真正的 Memory Manager 至少有四类工作：

1. **DECIDE**：add / reinforce / merge / update / conflict / ignore。
2. **RETIRE**：旧事实如何变为 historical、superseded、invalidated 或 archived。
3. **ATTRIBUTE**：记录来自哪个用户、消息、工具、模型与策略版本。
4. **REFLECT**：周期性跨会话复查重复、矛盾、过时内容和潜在新规律。

常见生命周期：

```text
candidate
  -> ignored
  -> review
  -> current
       -> reinforced
       -> superseded -> historical
       -> conflicted
       -> invalidated
       -> deleted/tombstoned
```

## 7. 三支柱的组合示例

需求：“用户用中文询问英文记录里的欠款，并要求保留修改历史。”

- Shape：PostgreSQL 版本表作为权威状态；pgvector 作为语义投影。
- Find：多语言 embedding + 姓名关键词 + scope 过滤 + rerank。
- Manage：金额修改时创建新版本，旧版本 retire，保留 provenance。

任何只回答其中一个支柱的产品或框架，都不是完整架构，只是其中一层。

- 为什么 RAG 是 Find，而不是一种完整的 Memory？
- 为什么 Graph 和 Vector 可以同时存在？
- 为什么程序性记忆比普通事实需要更严格的信任门？

## 9. 如何判定一条内容属于哪类记忆

使用这棵判定树：

```text
它只是当前任务中间状态吗？
  是 -> working memory / workflow state
  否 -> 它描述一次有时间边界的经历吗？
          是 -> episodic
          否 -> 它描述相对稳定的事实/偏好吗？
                  是 -> semantic
                  否 -> 它会改变以后“怎么做”吗？
                          是 -> procedural
                          否 -> 可能不属于 memory，或需要领域建模
```

一条 source 可以产生多种候选。例如：

```text
“昨天和 Alex 部署失败，因为漏跑迁移；以后上线前先验证 migration。”
```

- episodic：昨天与 Alex 的部署因漏迁移失败；
- semantic：Alex 参与该项目部署（是否持久化取决于价值）；
- procedural：上线前验证 migration；
- working：当前要修复部署，仅在任务完成前保留。

分类不是文本的唯一标签，而是不同生命周期与风险策略。

## 10. 一个可落库的 Memory Contract

```json
{
  "memory_id": "mem_...",
  "lineage_id": "lin_...",
  "scope": {"tenant": "t1", "user": "u1", "agent": "a1"},
  "type": "SEMANTIC",
  "subject": {"kind": "PERSON", "id": "paul-graham"},
  "predicate": "owes_amount",
  "value": {"amount": 200, "currency": "USD"},
  "normalized_content": "Paul Graham owes the user 200 USD.",
  "truth_state": "CURRENT",
  "valid_time": {"from": null, "to": null, "precision": "UNKNOWN"},
  "confidence": 0.96,
  "importance": 0.70,
  "sensitivity": ["FINANCIAL"],
  "provenance": [{"source_event_id": "evt_...", "actor": "DIRECT_USER"}],
  "schema_version": "memory.v1",
  "policy_version": "write-policy.v3"
}
```

设计含义：

- `content` 供人和语义检索，结构化 value 供精确计算与冲突判断。
- `confidence` 是证据属性，不是权限。
- `importance` 可做实验特征，不能默认覆盖 truth/ACL。
- `schema/policy version` 使未来重提取与迁移可解释。
- scope 和 provenance 是一等字段，不是日志附属品。

## 11. 不同类型的默认治理矩阵

| 类型 | 默认写入门槛 | 默认保留 | 典型更新 | 注入位置 | 高风险点 |
|---|---|---|---|---|---|
| Working | 低，任务内 | 短 | 原地状态机/快照 | run state | 跨任务污染 |
| Semantic | 中 | 中长 | reinforce/supersede/conflict | memory data | 错实体、过时事实 |
| Episodic | 中 | 策略定义 | append/correct/invalidate | memory data | 时间和来源错误 |
| Procedural | 高，需可信证据 | 长 | version/approve/rollback | developer/skill 层 | 持久指令注入 |

程序性记忆不应直接以普通 `<memory>` 数据片段进入 system 指令。安全做法是：候选 -> 测试/审核 -> 版本化 Skill -> 明确启用范围。

## 12. Shape/Find/Manage 的组合空间

同一个需求可能有多种合理组合：

| 场景 | Shape | Find | Manage |
|---|---|---|---|
| 个人 CLI，30 条偏好 | Markdown | 全量注入 | 人工编辑 |
| 本地桌面助手，500 条 | SQLite rows | FTS5 | 定期 consolidation |
| SaaS 用户画像，百万用户 | PostgreSQL rows + vector projection | hybrid + filters | 版本/权限/删除 |
| 研究关系网络 | temporal graph + source rows | vector entry + traversal | entity merge + edge validity |
| 稳定部署规则 | versioned Skills | applicability match | approve/retire/rollback |

产品比较时应填这张表，而不是问“谁的 memory 最强”。
