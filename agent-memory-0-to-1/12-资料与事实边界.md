# 12 资料与事实边界

## 本章导学

**学习目标**：建立一套可持续更新的研究方法，能区分一手证据、产品营销、本地实测和工程推断，避免快速变化的 Memory 生态让笔记悄悄过期。

**读完产出**：source ledger、固定版本源码笔记、可重放实验和每条 claim 的证据等级。

## 1. 使用原则

快速变化领域必须区分：

- `CONFIRMED`：官方文档/源码/论文或本地可复现实验直接支持。
- `UPSTREAM-REPORTED`：论文/厂商报告，尚未本地复现。
- `INFERRED`：基于证据的工程推断，不是产品保证。
- `HYPOTHESIS`：待 benchmark 验证。
- `DEPRECATED`：历史 API/架构，不能当现状。
- `NOT RUN`：未运行，不能填 0 或虚构数字。

## 4. 易过时/易误述结论

1. 不把某个 SDK 版本的默认行为说成整个产品永久能力。
2. 不把 mem0 当前 native graph 与早期外部 graph store API 混为一谈。
3. 不声称 Zep 使用 graph embedding，除非官方/源码明确是拓扑 embedding；给节点/边文本做 embedding 不等于 graph embedding。
4. 不把 LangMem 与数据库并列；它主要是 manager/library。
5. 不把 vendor benchmark 分数写成本地结果。
6. 不把 `accepted`、`processed`、`queryable` 当同一状态。
7. 不把 graph search 返回历史边理解为 lifecycle 没生效；需要检查 validity 和消费 contract。
8. 不把长上下文、summary、RAG 或 vector DB 单独称为完整长期记忆系统。

## 5. 笔记更新方法

每次更新产品章节：

1. 记录日期、SDK/version/commit、产品面（OSS/hosted）。
2. 先读官方 docs/changelog/source，再读二手文章。
3. 用隔离 namespace 跑最小实验。
4. 保存 raw request/response（脱敏）、timing、状态和截图/trace。
5. 把 confirmed、observed、inferred、unknown 分开写。
6. 旧结论不要直接覆盖，标记 deprecated/changed，保留演化背景。

## 6. 分阶段阅读路线

### 基础定义

先读 Agent Memory survey、OpenAI conversation/memory pattern、Anthropic context engineering。目标是建立 history/context/RAG/memory 边界，不急着比较产品。

### 工程机制

读 PostgreSQL transaction/locking/FTS、pgvector，再对照本地 MemOS architecture/ADR。目标是理解 authority、outbox、version、projection 和 failure windows。

### 产品与源码

按 `docs -> public API -> source -> local experiment` 顺序研究 mem0、LangMem、Graphiti/Letta。产品 docs 说明承诺，源码说明某个 commit 的实现，实验说明当前账号/配置的观测；三者不能互相替代。

### Evaluation 与安全

读 LoCoMo、LongMemEval、BEAM 的任务/metric/license，再读 memory poisoning 研究。先复现小子集和 evaluator，不直接复制论文结果。

## 7. Source Ledger 模板

```yaml
claim_id: C-...
claim: "..."
grade: CONFIRMED | UPSTREAM-REPORTED | INFERRED | HYPOTHESIS | DEPRECATED
product_surface: OSS | hosted | paper | local-experiment
source_url_or_path:
commit_or_version:
accessed_at: 2026-08-29
quoted_evidence:
local_reproduction:
  run_id:
  status: NOT_RUN | PASSED | FAILED | PARTIAL
scope_limitations:
supersedes_claim_id:
```

这让“当前 mem0 平台 graph always-on”与“旧 SDK 实验未启用 graph”可以同时成立，因为 product surface/version 不同。

## 8. 阅读论文的核查清单

- 研究的是模型 memory、Agent memory、RAG 还是 context？
- 数据集是否公开、license 是否允许重分发？
- baseline 是否同模型、同 token/evidence budget？
- retrieval、answer、LLM judge 是否混成一个指标？
- test 是否被用于调 prompt/threshold？
- 报告的是平均值还是 per-category、置信区间和失败样本？
- 使用的模型 alias 是否可能漂移？
- 结论是作者报告还是独立复现？
- 是否只在短会话测“长期”记忆？
- 成本是否含 memory formation/maintenance？

## 9. 阅读源码的核查清单

1. 固定 commit/tag 与 dependency lock。
2. 从 public API 追到 storage schema、write manager、retrieval 和 lifecycle。
3. 找异步 job/readiness、filters、delete、scope、provenance。
4. 阅读 tests，区分真实 provider test 和 fake/unit test。
5. 搜索 deprecated/migration/changelog。
6. 记录“源码中没找到”只是 N/E，不等于产品绝对没有。
7. 写最小原生脚本验证，不先套统一 abstraction。

## 10. 产品验证矩阵

| 维度 | 要核对的问题 |
|---|---|
| Write | 原句还是提取结果？add/update/delete/noop 谁决定？ |
| Readiness | API 返回、processed、queryable 是否分离？ |
| Lifecycle | superseded/invalid/current 在哪个 API 可见？ |
| Retrieval | vector/BM25/entity/graph 如何组合？历史是否返回？ |
| Time | event/valid/transaction time 支持到什么程度？ |
| Graph | node/edge 类型、ontology、provenance、是否可导出？ |
| Scope | tenant/user/agent/filter 在哪里执行？ |
| Delete | user/memory/project/ontology/derived state 如何清理？ |
| Portability | 能否导出完整状态并重建？ |
| Cost | formation/search/storage/graph/rerank/egress 如何计费？ |

## 11. 笔记变更记录规则

重大产品事实变化时，在相关章节保留：

```text
[CURRENT 2026-08-29] 当前官方能力与链接
[OBSERVED version X] 本地固定版本实验
[HISTORICAL] 旧 API/行为
[UNKNOWN] 尚未验证的差异
```

不要为了让笔记看起来整洁而删掉历史差异；理解 API/产品演化本身就是前沿工程能力。

## 12. 本章验收

- 任意产品 claim 都能说出 surface、version、date 和证据等级。
- 不把 vendor/paper 数字写成本地结果。
- 能解释“没有证据”与“证明不存在”的差异。
- 能从 docs 追到源码和最小实验，并保存 run artifact。
- 笔记过期时能标记演化，而不是静默覆盖。
