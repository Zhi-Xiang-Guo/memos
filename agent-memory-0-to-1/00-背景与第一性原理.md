# 00 背景与第一性原理

## 本章导学

**学习目标**：建立一个不会被产品名词带偏的 Agent Memory 心智模型，能从状态、成本、风险和效用四个维度判断一个需求是否真的需要长期记忆。

**前置知识**：知道 LLM 接收 token 并生成 token 即可，不要求理解 Transformer 数学。

**读完产出**：你应该能独立画出 `参数知识 / 当前上下文 / 外部状态` 三层图，列出至少 10 个 Memory 失败案例，并用一个反例击穿“向量库就是记忆”的说法。

## 1. 背景：为什么每次 LLM 调用都像从失忆开始

一次普通 LLM API 调用可以抽象为：

```text
output = model(parameters, current_input_tokens)
```

模型能使用的只有两类信息：

- **参数中的能力和世界知识**：训练后相对固定，不知道某个用户昨晚说了什么。
- **本次调用输入的上下文**：system/developer/user/tool 消息和附加材料；调用结束后不会自动成为下一次输入。

所以“模型记得上一轮”通常不是模型在内部形成了新记忆，而是宿主程序把历史消息再次发给了模型。新进程、新会话、上下文截断或换模型后，这种表面连续性就会消失。

### 长上下文为什么仍不等于记忆

把全部聊天塞进上下文能暂时缓解问题，但没有回答：

- 哪些信息值得跨月保留，哪些只是寒暄？
- 用户改口后哪个值是当前真值？
- 不同用户、租户、Agent 谁能读取？
- 怎么删除派生向量、缓存和摘要中的个人信息？
- 如何避免陈旧或恶意内容长期污染后续决策？
- 历史增长后每次都重传，成本、延迟和注意力会怎样？

因此长上下文是**工作记忆的容器**，不是完整的长期记忆生命周期。

## 2. Agent Memory 解决什么问题

### 2.1 连续性

跨会话保留偏好、人物关系、项目决策、承诺和历史事件，让 Agent 不必每次重新询问。

### 2.2 个性化

根据用户稳定偏好调整结果，例如输出风格、会议时间、饮食禁忌。这里必须区分稳定偏好与一次性要求。

### 2.3 长期任务

跨数小时、数天或多个 run 保留目标、进度、失败尝试和恢复点。

### 2.4 事实演化

现实会变化。地址、会议时间、项目状态会更新。系统既要回答“现在是什么”，又要回答“过去是什么、何时改变”。

### 2.5 经验复用

把成功/失败轨迹归纳为可复用步骤，即程序性记忆；但这类记忆能影响行为，写入门槛应高于普通事实。

## 3. 第一性原理：把问题拆成不可混淆的层

### 原理一：推理是瞬时计算，记忆是持久状态

LLM 生成回答属于计算；Memory 属于状态管理。状态系统必须关心身份、版本、权限、时间、并发、删除和恢复，不能只关心“模型能不能理解”。

### 原理二：证据不等于解释

聊天原文是证据；“用户偏好上午开会”是从证据提取的解释。证据应可追溯，解释应可版本化和重建。

```text
source_event -> extraction_run -> candidate -> accepted_memory_version
```

如果解释错了，可以修正解释而不是伪造历史。

### 原理三：存储形态、查找方式、维护策略是三件事

- **Shape**：文件、关系行、向量、图。
- **Find**：全量注入、关键词、向量、混合、图遍历。
- **Manage**：添加、合并、更新、失效、归档、删除、反思。

RAG 回答的是 Find，不自动解决 Shape 与 Manage。Graph 是一种表示/遍历能力，不天然替代 RAG。

### 原理四：相关不等于正确

向量相似度只说明文本语义接近。它不证明：

- 事实仍然有效；
- 来源可信；
- 当前用户有权读取；
- 两句话指同一个实体；
- 旧事实应被新事实替代。

因此检索分数不能拥有业务真值的决定权。

### 原理五：漏记和错记的风险不对称

漏掉一个偏好，Agent 可能再问一次；写入一个错误或恶意规则，它可能影响未来很多次会话。因此长期写入通常应优先提高 precision，并允许 `IGNORE`、`REVIEW`、`CONFLICTED`，而不是“全都记”。

### 原理六：权威状态与加速索引分离

关系表/事件日志保存真值、版本和溯源；FTS、Embedding、图和缓存是可重建投影。索引失败或模型升级不能改变事实本身。

### 原理七：记忆的价值由未来任务衡量

“成功写入 1000 条”不是质量。真正指标是：未来问题能否召回正确、当前、授权、足够的证据，并改善回答或行动，同时控制延迟、成本和风险。

## 4. 一个可操作的定义

> Agent Memory 是从有来源的经验中，经选择和治理形成的持久状态；它能随新证据演化，并在未来任务中按查询、时间、权限和 token 预算选择性重建为工作上下文。

定义中的必要条件：

1. 选择性写入，而非全量保存。
2. 版本与状态演化，而非静态 append-only 文本堆。
3. provenance 与 scope，而非匿名片段。
4. 选择性召回，而非每次全塞。
5. 下游效用评估，而非只测相似度。

## 5. 与相邻概念的边界

| 概念 | 主要目的 | 是否跨会话 | 是否管理真值演化 | 典型实现 |
|---|---|---:|---:|---|
| Chat history | 重放对话 | 可选 | 否 | message log |
| Context window | 当前推理输入 | 单次调用 | 否 | tokens |
| Cache | 避免重复计算 | 可 | 否 | KV/response cache |
| RAG | 找外部证据 | 可 | 通常否 | retriever + generator |
| Agent Memory | 治理个体/任务经验 | 是 | 是 | lifecycle + store + retrieval |
| Workflow state | 业务流程当前状态 | 是 | 由领域状态机管理 | task/order DB |
| Fine-tuning | 改变通用行为/能力 | 是 | 更新慢、不可逐条审计 | parameter update |

关键判断：订单状态、余额、库存等应由业务系统权威管理，Memory 只能保存与它们有关的证据或可检索投影，不能替代领域数据库。

## 6. 最小反例：为什么 `Embedding + Vector DB + TopK` 不够

已存两条：

```text
m1: Elon will arrive at 7 PM.   status = superseded
m2: Elon will arrive at 9 PM.   status = current
```

问题：“Elon 几点到？”

两个句子与问题几乎同样相似。向量 TopK 可能把旧值排在前面。正确系统必须先知道状态和时间，再谈相似度：

```text
authorized AND current AND valid_at(now)
-> candidate retrieval
-> ranking
-> context
```

这就是从 Demo 到生产 Memory 的分界线。

## 8. 更严格的系统模型

把一次带记忆的 Agent 决策写成：

```text
M_t      = t 时刻的权威记忆状态
E_t      = 新到达的有来源事件
W        = 写入/治理策略
M_{t+1}  = W(M_t, E_t)

q_t      = 当前问题
R        = 候选召回器
P        = 权限、真值、时间与预算策略
C_t      = P(R(q_t, M_t))

a_t      = LLM(parameters, instructions, working_state, C_t, q_t)
```

这里有三个重要结论：

1. LLM 不是状态转移的唯一所有者，`W` 中有大量必须确定化的规则。
2. 检索 `R` 只产生候选，`P` 决定哪些证据有资格进入上下文。
3. 最终答案错误不等于 `R` 错；也可能是 `W`、`P` 或 LLM 使用证据失败。

这套分解后来会自然对应 write、manage、read 和 answer 四类测试。

## 9. Memory 的成本模型

长期记忆不是免费能力。一次写入的总成本可以粗略表示为：

```text
C_write = C_extract + C_policy + C_embed + C_storage + C_index + C_audit
C_read  = C_gate + C_query_understand + C_retrieve + C_rerank + C_context + C_generation
C_life  = C_write + N_reads*C_read + C_maintenance + C_deletion + C_incident
```

其中最常被忽视的是维护、删除和事故成本。一个“全记住”的 Demo 会让 `C_extract` 看起来很低，却把噪声、隐私和错误放大到未来每次 read。

是否值得写入，可以用期望效用思考：

```text
remember if:
P(future_use) * value_when_correct
  > write_cost + privacy_risk + P(wrong) * downstream_harm
```

这不是要求线上真的计算精确货币值，而是提醒你：高频稳定偏好与一次性寒暄的收益结构不同；支付指令和普通颜色偏好的错误代价也不同。

## 10. 从产品需求推导 Memory 需求

面对“给 Agent 加记忆”的模糊需求，依次问：

1. **要跨越哪个边界**：一次调用、一个 session、一个任务、一个设备还是数年？
2. **记忆对象是谁**：用户、项目、Agent、团队、实体还是业务订单？
3. **未来如何使用**：回答问题、个性化、工具行动、恢复任务还是训练策略？
4. **会不会变化**：是否需要 current、history、as-of、conflict？
5. **错了会怎样**：多问一次、回答错误、越权泄漏还是执行错误转账？
6. **谁能修改/删除**：用户、管理员、模型、后台任务、合规系统？
7. **如何证明有用**：什么任务、control 和 baseline 能反驳“没有 memory 也能答”？

如果真实需求是“恢复订单处理步骤”，优先使用 workflow state machine；如果是“回答内部文档”，优先 RAG；如果是“跨会话保留用户可更新偏好”，才进入长期 Memory。

## 11. 失败面矩阵

| 阶段 | 最小失败案例 | 结果 |
|---|---|---|
| 写入选择 | 把寒暄当长期偏好 | 污染和 token 浪费 |
| 提取 | 把“Alex 不喝咖啡”提成“喜欢咖啡” | 错误状态长期复用 |
| 身份 | 两个 Alex 被合并 | 串人 |
| 时间 | 7 点改 9 点仍返回 7 点 | stale answer |
| 权限 | team Agent 读到 private memory | 数据泄漏 |
| 检索 | 中文问题找不到英文事实 | recall miss |
| 排序 | superseded 文本分数更高 | 旧事实泄漏 |
| 上下文 | 正确证据被截断 | context miss |
| 生成 | 模型忽略正确证据 | reasoning miss |
| 删除 | 旧 projection/job 复活数据 | 合规失败 |
| 反思 | 模型从一次偶然失败学出永久规则 | 自我强化错误 |
